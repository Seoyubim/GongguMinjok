[heading_2] 배경 — 왜 이 기능이 필요한가?
[paragraph] 기존 updateGroupBuy()는 상태 체크 없이 모든 필드를 수정할 수 있었다. 이로 인해 아래 문제가 발생했다.
[bulleted_list_item] 결제 진행 중(CLOSED)인 공구의 금액을 수정할 수 있었음
[bulleted_list_item] 픽업 대기 상태에서 픽업 장소를 바꾸는 등 참여자에게 피해를 줄 수 있었음
[bulleted_list_item] 마감일을 단축하거나 무제한 연장할 수 있었음
[bulleted_list_item] 과거 시간으로 픽업 시간을 추가할 수 있었음
[bulleted_list_item] 참여자가 이미 선택한 픽업 시간을 삭제할 수 있었음
[paragraph] 이번 브랜치에서 위 문제들을 모두 해결했다.

[heading_2] 핵심 변경 포인트
[paragraph] 1. HOST_PURCHASED 상태 추가
[paragraph] 기존 7개 상태에서 8개로 확장되었다. HOST_PURCHASED는 정원 충족 + 전원 결제 완료 후 호스트가 실제로 상품을 구매 완료한 상태를 의미한다. 이 상태에서도 일부 필드 수정이 허용된다.
[code] 상태 전환 흐름:
OPEN → CLOSING → CLOSED → PAYMENT_COMPLETED → HOST_PURCHASED → PICKUP_READY → COMPLETED
                                                                                    ↘ EXPIRED
[paragraph] 2. originalDeadline 필드 추가
[paragraph] 최초 게시글 생성 시 입력된 deadline 값을 별도로 저장한다. @Column(updatable = false)로 선언되어 있어 이후 어떤 수정도 DB에 반영되지 않는다.
[paragraph] 이 필드가 필요한 이유: deadline을 연장할 때 "최대 7일"을 현재 deadline 기준으로 잡으면, 7일씩 계속 연장하는 우회가 가능해진다. originalDeadline을 기준으로 잡으면 이 문제가 해결된다.
[code] 예시:
originalDeadline = 2026-05-01
current deadline = 2026-05-06 (한 번 연장된 상태)
새 deadline 요청 = 2026-05-09 → originalDeadline + 7일(2026-05-08) 초과 → 예외
[heading_2] 추가된 코드

[code] private void validatePickupTimes(List<LocalDateTime> pickupTimes, LocalDateTime deadline) {
    LocalDateTime now = LocalDateTime.now();
    LocalDateTime maxAllowed = deadline.plusDays(14);

    for (LocalDateTime time : pickupTimes) {
        if (time.isBefore(now)) {
            throw new IllegalArgumentException("픽업 시간은 현재 시간 이후여야 합니다.");
        }
        if (time.isAfter(maxAllowed)) {
            throw new IllegalArgumentException("픽업 시간은 마감일로부터 14일 이내여야 합니다.");
        }
    }
}
